# Lidera

Сквозная аналитика рекламы до реальной продажи: Meta Ads и TikTok Ads → лид → пробный →
продажа → выручка. Multi-tenant SaaS на Next.js + Supabase.

Текст исходного ТЗ — в [PROMPT.md](./PROMPT.md).

### Изоляция арендаторов

Каждая строка данных клиента несёт `company_id`. Доступ ограничен политиками Row Level
Security, а не фильтрами в интерфейсе:

* `private.current_company_id()` — компания текущего пользователя;
* `private.is_super_admin()` — платформенный администратор видит всё;
* `private.can_write()` — право записи внутри своей компании.

Функции живут в схеме `private`, поэтому не доступны через `/rest/v1/rpc`, и объявлены
`security definer` — иначе политика на `profiles`, читающая `profiles`, ушла бы в рекурсию.

Проверено на живой базе: директор видит только свою компанию, не может создать компанию
(403) и не может вставить строку с чужим `company_id` (ошибка политики RLS).

## Тип воронки компании

Не у всех клиентов есть промежуточный шаг «пробное занятие»: онлайн-школа ведёт лид
через пробный урок, товарный бизнес продаёт сразу. Поле `companies.funnel_type`
переключает кабинет между двумя моделями:

| | `trial` | `direct` |
|---|---|---|
| Воронка | Лид → Пробный → Продажа | Лид → Контакт → Продажа |
| KPI и колонка в таблице креативов | «Пробные» | «Дозвон» |
| Раздел «Пробные» в меню | есть | скрыт |
| Статус «Пробный» у лида | доступен | недоступен (проверка и в форме, и на сервере) |

Тип задаёт администратор при создании компании и меняет директор в настройках.
Промежуточный шаг считается в одном месте — `middleStepValue()` в `lib/metrics.ts`,
поэтому новую модель воронки можно добавить, не трогая страницы.

## Статусы лида

Менеджер оценивает лид результатом контакта, а не абстрактной «работой». Набор,
подписи, стадии и правила воронки лежат в одном файле — `lib/lead-status.ts`;
оттуда их берут выпадающие списки, валидация серверных действий и сводки.

| Статус | Смысл | Стадия |
|---|---|---|
| `new` | заявка пришла, её ещё не трогали | новые |
| `no_answer` | «Игнор» — не отвечает | игнор |
| `contacted` | «Дозвон» — разговор состоялся | в работе |
| `in_progress` | переговоры продолжаются | в работе |
| `thinking` | взял паузу на решение | в работе |
| `trial` | записан на пробное (только воронка `trial`) | в работе |
| `sale` | оплата прошла | купили |
| `rejected` | поговорили, покупать не будет | потеряны |

Шаг воронки «обработан» = **был живой контакт** (`isReached`). Отказ сюда входит —
с человеком поговорили; игнор не входит. Поэтому продажи всегда вложены
в обработанных, и воронка не «расширяется» на среднем шаге.

## Сотрудники

Платформу видит **только директор компании** (и платформенный администратор).
У сотрудника нет учётной записи и входа в кабинет: он заведён строкой в
`employees`, а работать будет через Telegram-бот — под него уже есть поля
`telegram_user_id` и `telegram_username`, привязка появится на следующем этапе.

| Роль | Что делает | Получает лиды |
|---|---|---|
| `rop` | руководитель отдела продаж | нет |
| `manager` | принимает лиды, дозванивается, ведёт по воронке | да |
| `salesperson` | проводит пробное и закрывает продажу (только воронка `trial`) | нет |

Увольнение мягкое: `status = 'fired'` + дата, строка остаётся — отчёты за прошлые
периоды не должны меняться задним числом. Активные лиды уволенного освобождаются,
чтобы не зависли на том, кто уже не работает.

Вход сотрудника в бот — по одноразовой ссылке `t.me/<бот>?start=<токен>`: директор
жмёт «Пригласить», платформа выдаёт ссылку на 48 часов и гасит прежние ссылки
этого человека. Смена (`shifts`) — выключатель для будущей авто-раздачи: частичный
уникальный индекс не даёт открыть две смены одному сотруднику.

Раздел «Команда» показывает по каждому за выбранный период: лиды, дозвон,
продажи и выручку. Выручка считается по лидам, где человек указан ответственным.
В таблице лидов есть столбец «Ответственный» — пока назначается вручную,
авто-раздача встанет на это же поле.

Раздел «Лиды» показывает разбор по статусам и четыре показателя отдела: всего,
дозвонились, купили и «ждут первого касания» — новые лиды старше суток.
Сводка считается отдельным запросом по всему периоду, а не по видимым 200 строкам.

## Авто-раздача лидов

Лид не должен лежать без хозяина, и не должен висеть на том, кто его не берёт.
Правила — в `lib/lead-distribution.ts`, три настройки у каждой компании
(«Настройки → Раздача лидов»):

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `auto_assign` | включена | раздавать ли автоматически |
| `max_open_leads` | 15 | сколько активных лидов может висеть на менеджере |
| `sla_minutes` | 10 | сколько даётся на первое касание |

Как это работает:

1. лид получает только менеджер с **открытой сменой** — смена и есть выключатель;
2. из них выбирается наименее загруженный, при равенстве — тот, кто дольше всех
   не получал лидов (честная очередь, не зависит от порядка имён);
3. упёршийся в лимит менеджер новых лидов не получает;
4. если за `sla_minutes` статус так и остался «Новый», лид возвращается в очередь
   и уходит **другому** — тому же он вернётся только если свободных больше нет;
5. никого на смене — лид ждёт в очереди и достаётся первому, кто её откроет.

Раздача запускается при создании лида, при открытии смены и раз в минуту из
самой базы: `pg_cron` + `pg_net` дёргают `POST /api/cron/distribute`. Планировщик
Vercel для этого не годится — на бесплатном тарифе он срабатывает раз в сутки,
а возврат по SLA должен происходить через минуты.

Отдельной переменной для доступа к этому адресу нет намеренно: ключ — это
`sha256` от сервисного ключа Supabase, который и так есть у обеих сторон.
В базе (Vault) лежит только хеш, сам ключ по сети не ходит.

Каждое назначение пишется в `lead_assignments` с причиной (`auto`, `manual`,
`sla`, `fired`). Без журнала не разобрать спор «мне лид не приходил» и не
посчитать честную очередь.

## Смены, геолокация и посещаемость

Режим смены задаётся компании («Настройки → Смены и офис») и при необходимости
переопределяется каждому сотруднику лично («Команда → График»). Это не роскошь:
в одной компании обычно есть и офисный отдел, и менеджеры из дома.

| Режим | Что значит |
|---|---|
| **Без смены** | лиды идут менеджерам всегда, отмечаться не нужно |
| **По кнопке** | лиды получает только тот, кто нажал «Я на смене» — для удалёнки |
| **По кнопке и геолокации** | смену можно открыть только рядом с офисом |

В режиме `geo` бот просит отправить геолокацию — Telegram отдаёт её только по
нажатию кнопки, тихо определить место сотрудника нельзя, и это правильно.
Расстояние считается по формуле гаверсинуса (`lib/geo.ts`) и записывается в
смену: спор «я был на месте» решается фактом. Радиус меньше 50 метров поставить
нельзя — точность GPS в городе хуже, и сотрудник в офисе получал бы отказ.

График работы — это рабочие дни недели, начало и конец дня и допустимое
опоздание. Он задаётся компании и может быть личным у любого сотрудника: в
карточке «Команда → График» переключатель «Как в компании / Свой». Редактор
один и тот же на обоих экранах (`components/app/work-schedule.tsx`): дни
выбираются кнопками с готовыми 5/2, 6/1 и 7/0, время — часами, и рядом сразу
видно длину смены и недельную норму часов. Конец раньше начала — это ночная
смена через полночь, а не ошибка.

Опоздание считается по местному времени компании (`timezone`), а не по времени
сервера, и только в рабочий по графику день: вышел в свой выходной — отметки
«опоздал» не будет.

«Как в компании» пишет в базу NULL — так общее правило меняется в одном месте и
доходит до всех, у кого нет исключения. Действующие правила собирает
`resolveShiftRules()`; бот, раздача и интерфейс берут их оттуда, а не считают
каждый по-своему.

Табель (`attendance`) — одна отметка на сотрудника в день. «На смене» и
«Опоздал» ставит система по фактическим сменам; больничный, отпуск, выходной и
удалёнку проставляет директор в разделе «Посещение». Ручная отметка сильнее
автоматической: открытие смены не затирает проставленный больничный.
Набор статусов компания выбирает из общего справочника — так отчёты по разным
компаниям остаются сравнимыми.

## Реклама и валюта

Раздел «Реклама» считает из `ad_metrics` — дневных строк, которые отдаёт рекламный
кабинет. Наполняет их `lib/meta-sync.ts`: раз в сутки (pg_cron → `/api/cron/meta-sync`,
03:30 UTC) платформа сама ходит в Meta Marketing API и перезабирает последние
30 дней целиком — Meta уточняет вчерашние цифры ещё пару дней, поэтому
дописывать их было бы неверно. Токен даёт только чтение (`ads_read`). Для кампаний с целью «переписки» поле `leads` хранит начатые переписки:
для такой рекламы написавший человек и есть лид.

Кампания несёт номер WhatsApp (`campaigns.whatsapp_number`), поэтому в разделе
видно, **на какой номер сколько людей написало и почём**. Номер берётся из
настроек группы объявлений (`promoted_object.whatsapp_phone_number`); если Meta
его не отдала, показываются последние цифры из названия кампании в виде «…8045» —
достраивать номер догадкой нельзя, правдоподобная выдумка хуже пропуска.

Креативы синхронизируются вместе с метриками: на уровне объявления видно, какой
ролик принёс переписки. Раздел «Креативы» — список того, что за период работало
(тратило бюджет или приводило людей); нажатие на строку открывает отдельный
экран с проигрывателем и всеми цифрами. Плееров в списке нет намеренно: десяток
роликов на одной странице грузится долго и мешает сравнивать. Ссылки Meta подписаны и живут недолго,
поэтому храним идентификатор ролика, а `/api/creatives/[id]/media` получает
свежий адрес на сервере и отправляет туда браузер: токен наружу не уходит, а
чужой креатив не отдаётся — строка читается под сессией пользователя, через RLS.
Обложку берём в исходном размере: превью 64×64 Meta режет по центру и обрезает
людям лица.

Валюта — своя у каждой компании (`companies.currency`): Meta списывает у одного
клиента тенге, у другого доллары, и подписать долларовый расход знаком тенге
значит соврать. `formatMoney` принимает валюту, страницы берут её из компании.

## Диапазон дат

Один компонент `DateRangePicker` на всех разделах с метриками: девять пресетов
(сегодня, вчера, 7/30/90 дней, эта и прошлая неделя, этот и прошлый месяц) плюс
произвольный диапазон, который выбирается двумя кликами по календарю.

Состояние живёт в адресе страницы — `?period=last_month` или
`?from=2026-07-01&to=2026-07-15`, — поэтому ссылку на конкретный период можно
переслать коллеге. Некорректные значения молча заменяются диапазоном по умолчанию.

## Графики

Цвета серий (`--color-series-revenue`, `--color-series-spend`) подобраны под тёмную
поверхность и проверены на различимость при дальтонизме и контраст к фону. Они намеренно
отделены от лаймового акцента интерфейса: акцент — для кнопок, серии — для данных.

Выручка и расход лежат на одной шкале в тенге; второй оси Y нет — при разных шкалах она
создаёт корреляцию, которой в данных не существует.

## Деплой на Vercel

1. Импортировать репозиторий, framework определится автоматически.
2. Добавить четыре переменные окружения из таблицы выше (`NEXT_PUBLIC_SITE_URL` —
   боевой адрес, например `https://lidera.kz`).
3. В Supabase → Authentication → URL Configuration добавить боевой домен и
   `https://<домен>/auth/confirm` в Redirect URLs — иначе не заработает восстановление пароля.

Рекомендуется включить Supabase → Authentication → Password protection →
проверку паролей по базе утечек: это единственное оставшееся предупреждение линтера
безопасности, и оно снимается только в интерфейсе Supabase.

## Что дальше

Схема уже рассчитана на следующие этапы и не потребует переписывания:

* **Meta Ads / TikTok Ads** — иерархия `ad_accounts → campaigns → ad_sets → ads → creatives`
  повторяет модель обоих API; внешние идентификаторы хранятся в `external_id`,
  синхронизация пишет в `ad_metrics`.
* **Telegram-бот и OCR** — таблица `receipts` со статусами проверки, полем `source`
  и `ocr_raw` для сырого ответа распознавания.
* **Сотрудники** — роли `MANAGER` и `EMPLOYEE` уже разрешены схемой и учтены в политиках.
* **Биллинг** — таблица `subscriptions` с планом и статусом.
